## What this is

A cross-vendor reimplementation of **Nvidium** (MCRcortex, LGPL-3.0) — the
mesh-shader terrain renderer that made NVIDIA cards render enormous view
distances at playable framerates — rebuilt on:

- **Minecraft 26.2's vanilla Vulkan backend** (verified present in the
  jar: `VulkanBackend`, `VulkanDevice`, `VulkanInstance`, …), instead of
  Nvidium's Sodium+OpenGL host. Riding the vanilla device deletes the
  GL↔VK interop problem entirely.
- **`VK_EXT_mesh_shader`**, the cross-vendor extension, instead of
  `GL_NV_mesh_shader` which only NVIDIA ever implemented. OpenGL never got
  AMD/Intel mesh shaders and never will (GL froze at 4.6/2017) — Vulkan is
  not a preference, it is the only road.

**Hardware target:** anything with `VK_EXT_mesh_shader` — AMD RDNA2+
(RX 6000+, Steam Deck, Ryzen 6000+ iGPUs), NVIDIA Turing+ (GTX 16xx+),
Intel Arc + Meteor-Lake-and-later iGPUs. Windows + Linux. Primary dev
hardware: the owner's RX 9070 XT (RDNA4, Windows 11).

## Non-goals (owner-ruled, 2026-08-09)

- **Shader-pack (Iris) support** — parked until the mod is complete; "a
  far off pipe dream". Cost accepted now: the terrain path lives behind
  one clean interface so a future compat layer has a seam.
- **A fallback renderer for hardware without mesh shaders** — such
  hardware keeps vanilla rendering (see the OpenGL-fallback requirement
  below, which handles the adjacent case gracefully).
- macOS.

## Standing requirement — the graceful OpenGL fallback

Owner directive (2026-08-09, verbatim): *"make sure the mod has the proper
code to turn off if the opengl rendering engine is on instead of vulkan
and it gives you a little popup saying how too, and maybe even has a
button to enable it on the popup."*

So, as a first-class deliverable (wave 1, testable before any mesh shader
exists):

1. On the OpenGL backend, Meshelium **disables itself completely** — no
   mixin side effects (the device-creation mixin is structurally a no-op
   on the GL path), no log spam, no crash.
2. A **one-time popup** at the title screen: Meshelium is installed but the
   game is on the OpenGL renderer; here is what Vulkan is and how to
   switch.
3. The popup carries an **[Enable Vulkan] button** that writes the vanilla
   backend option itself. GPU backends swap at boot, so the button applies
   the setting and prompts for a restart (offer [Restart now] if the
   platform makes that sane, else clear instructions).
4. **No nag loop:** "don't show again" persists; the popup also stops
   appearing once Vulkan is active. Config can re-enable it.
5. The same gate handles "Vulkan but no `VK_EXT_mesh_shader`" with a
   different, honest message (hardware/driver too old) — and Meshelium
   stays off.

✅ *Exact backend option key/mechanism:* answered (seam Q1) and implemented
in wave 1 — `options.preferredGraphicsBackend().set(VULKAN)` + `save()` from
the popup's [Enable Vulkan], then a restart hand-off ([Quit Game]/[Later]).

   vanilla VULKAN backend, and no Sodium is known to run on it.** Sodium
   is a GL-era renderer whose 26.2 existence is unverified — and
   Alphadium's history shows the GpuDevice refactor forcing shims at
   every draw boundary, i.e. the Sodium ecosystem strains against exactly
   the abstraction we ride. Pinning the mod's existence to an unverified
   third-party Vulkan port is not a plan. Secondary reasons: Alphadium
   proved 100% of maintenance churn lands at the HOST boundary (GPU core
   byte-identical across MC 1.21→1.21.11 + Sodium 0.5→0.8.6) — with
   vanilla as host, host churn and game-version churn are the SAME churn,
   paid once per MC version we'd track anyway; and vanilla equivalents
   exist for the heaviest consumed pieces (section build interception for
   the mesher plug, `SectionOcclusionGraph` for the BFS tracker — mapped
   by the wave-2 recon, = architecture Q11 + seam Q4). Cost accepted: we
   own the CPU side (facing-bucketed encoder, section store + rebuild
   queues, options UI, shader preprocessing).
   **Porting baseline: Alphadium, not raw Nvidium**, where they diverge —
   its KHR-subgroup compute command-buffer builder, compacted section
   indices, separate per-pass command buffers, optional barycentric, and
   host-side translucency sorting are already half-way to Vulkan
   (architecture §9/§13). Also adopted at design time: drop
   representative-fragment-test (stores are idempotent — correctness
   unaffected; Hi-Z is Q3's possible upgrade), and the known-bug fix list
   (architecture Q13: sectionBuffer 39k/50k sizing, readback overflow,
   page-decommit fencing, camera snapshot race).
   Architecture questions 2–16 form the standing design ledger; each gets
   resolved in the wave that touches it, in the SPEC, with citations.
3. ~~**SPIR-V toolchain**~~ **ANSWERED** (seam Q5): vanilla compiles GLSL
   at runtime (`vulkan/glsl/GlslCompiler`, SPIRV-Cross reflection), so
   shaderc natives ship with the game — but its `ShaderType` is
   VERTEX/FRAGMENT only, so Meshelium drives shaderc directly for
   task/mesh stages and owns its pipeline objects. No build-time shader
   toolchain. (Caps probe verifies mesh-stage support in the shipped
   natives on real hardware.)
4. ~~**Pipeline creation style**~~ **ANSWERED** (seam Q6): Vulkan 1.2 +
   sync2 + **dynamic rendering** via feature structs; no legacy render
   passes anywhere. Mesh pipeline uses `VkPipelineRenderingCreateInfo`.
5. **Vanilla terrain draw path on the Vulkan backend** (seam Q4) — the
   wave-2 recon; where section draws are recorded and where Meshelium's
   command submission slots in.
