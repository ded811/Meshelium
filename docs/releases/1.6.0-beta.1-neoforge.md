**Meshelium now runs on NeoForge.** This is the first NeoForge build, out as
a beta while it gets tested on machines other than the one it was built on.
It is the same mod as the Fabric build — same renderer, same settings, same
speed — because both loaders are built from one shared set of code and only
differ in the few lines each needs to start up.

Client-side only. Your friends do not need it and neither does your server.

---

## The NeoForge + Vulkan crash, and why you will not hit it

If you have tried turning Vulkan on with NeoForge before, you have probably
seen the game die on startup with an error blaming your graphics drivers.

**Your drivers are fine.** Here is what is actually going on.

NeoForge shows its own little loading screen before Minecraft properly
starts. To draw that screen it creates the game window in OpenGL mode. But
Meshelium only works on Minecraft's *Vulkan* renderer, and Vulkan cannot
draw into a window that was made for OpenGL. Minecraft asks for one, gets
refused, and the game stops before it ever reaches the main menu.

This is not a Meshelium bug — it happens to any NeoForge player who switches
to Vulkan, with or without this mod. It just hits Meshelium players every
single time, because Vulkan is the only renderer Meshelium runs on at all.

**You do not have to do anything about it.** Meshelium closes that loading
screen at the last possible moment before the game makes its window, so the
game starts normally and you never see the error.

What you will actually notice:

- No NeoForge loading screen.
- The game window appears a moment later than it used to.

That is the whole difference. If you are running OpenGL, none of this
happens and your loading screen is left exactly as it was.

## The technical version

For anyone who wants it. Skip this if you just want to play.

**The failure.** GLFW error 65540 — *"Vulkan: Window surface creation
requires the window to have the client API set to GLFW_NO_API"*. NeoForge's
early loading screen (`earlyWindowControl` in `config/fml.toml`) owns a GLFW
window carrying an OpenGL context and hands that same window straight to
Minecraft. `glfwCreateWindowSurface` then refuses it, and the game dies
inside `Minecraft.<init>` before any mod-facing screen exists — which is why
what you get is a raw GLFW dialog telling you to update drivers that were
never involved. Upstream issue: **neoforged/NeoForge#3230**. The proper fix,
PR #3259, reworks the early screen onto Blaze3D and is not merged yet, so no
NeoForge build carries it today.

**The workaround.** `Window.createGlfwWindow` asks, exactly once, whether an
early screen already exists. Meshelium answers "no" at that call when the
Vulkan backend is the one starting up. Vanilla then takes the branch it
already has for players who never had an early screen: it creates its own
window, with the window hints the Vulkan backend set a few instructions
earlier. On OpenGL the answer is passed through untouched.

That call site is the only place this can be done. It is on the main thread,
after the backend is known, after the hints are set, and before the window
exists. Two earlier approaches were tried and abandoned: a
`GraphicsBootstrapper` service runs early enough but makes NeoForge treat
the mod's own jar as a service rather than a mod, so Meshelium vanished from
the mod list entirely; and the mod entrypoint runs before the game window
but long after the early window, on a worker thread where GLFW calls are
illegal.

**Taking the screen apart, in the order that matters.** Each step here was
learned from a failure:

1. **Mark the screen closed first.** NeoForge's client mod loader captured a
   direct reference to that screen's tick during startup and never re-checks
   whether the screen is still registered. A tick that repaints has to draw,
   and under Vulkan the main thread has no OpenGL binding at all — so it dies
   in native code and takes the whole JVM with it, with no crash report and
   nothing a player could act on.
2. **Clear the provider**, so everything that does check reaches the same
   state NeoForge itself uses when the loading screen is turned off. That is
   a configuration NeoForge supports and every consumer already handles.
3. **Take the window and destroy it, last.** The handover can only happen
   once — it clears the window's size callback on the way through, so a
   second attempt dies on a null. If Meshelium took the window and then gave
   up, the game's own attempt a few instructions later would be that second
   attempt. So the handover is the final step that can still be backed out
   of, and after it the job always finishes.

Anything that fails before that last step changes nothing at all: the game
is left exactly as NeoForge set it up.

**Belt and braces.** Meshelium also writes `earlyWindowControl = false` into
`config/fml.toml`. That only matters if a future NeoForge build moves the
code the live fix hooks into — then your first launch fails and the second
one works, instead of failing forever.

## Also fixed in 1.6

- **Meshelium did nothing at all if you skipped the main menu.** Launching
  straight into a world — quick play, or a launcher's "resume last world" —
  left the mod switched off for the entire session, with nothing in the log
  to say why. It waited for a title screen before checking whether your
  machine could run it, and if you never saw one, it never checked.
- **The "switch to Vulkan" offer could disappear for good after you accepted
  it.** Pressing *Enable Vulkan* silently counted as pressing *Don't Show
  This Again*.
- **A squared-off bite of missing ground and water** at the edge of the
  loaded area, on the side you were moving away from.
- **The ground and the ocean below you emptying out** when you fly upward.
- **Water and glass vanishing** while the land beside them stayed.

## What you need

- **Minecraft 26.2** on **NeoForge for 26.2** (any 26.2.x build; this was
  built and tested against 26.2.0.75). A NeoForge for 26.3 will refuse to
  load it rather than half-work — every mixin is pinned to 26.2's bytecode,
  so loading half of them and rendering nothing would be the worse
  outcome.
- **Minecraft's Vulkan renderer**: Options → Video Settings → Graphics API →
  Vulkan, then restart. Meshelium offers to switch it for you the first time
  it sees you on OpenGL.
- A graphics card with mesh shaders: **AMD** RX 6000 or newer, **NVIDIA**
  GTX 16xx or newer, or **Intel** Arc. Laptop and handheld chips count,
  including the Steam Deck.
- **Windows or Linux.** No macOS — Macs do not do mesh shaders on Vulkan.
- Nothing else. No API mod is required on NeoForge.

If your card cannot do mesh shaders, Meshelium switches itself off, tells
you why, and your game carries on normally.

---

## Why this is a beta

It is the first NeoForge release, and it has been tested on one machine — an
AMD RX 9070 XT on Windows 11. The renderer underneath is the same code the
Fabric build has been running, and it has been checked on NeoForge end to
end: booting straight into a world, rendering it, and shutting down with
nothing left allocated. What has not been tested is other people's hardware
and other people's mod lists.

If something goes wrong, the log is worth attaching — Meshelium writes down
what it decided and why at startup.
