## 1. Threading ground truth (proofs used below)

- **pump**: render thread only, inside vanilla's dispatcher.lock()==copyLock window — MTP:19-22 (hook = LevelRenderer.render right after uploadTerrainBuffersToGpu), MTP:73, MTP:125; TR:43-45. Releases can never interleave with a pump (both need copyLock).
- **onMeshReleased**: any thread, always under copyLock — RSM:26-35, RSM:104-116. Worker-thread instances proven: doTask's empty-mesh and cancelled-mid-copy releases (TR:80-84 bytecode census) and the upload seam's own `checkSectionMesh` call at RSM:214, which runs on whatever thread runs addSectionBuffersToUberBuffer (build worker or render thread, RSM:119-131). Render-thread-only instances: releases inside a reset() bracket — both reset() callers are render-thread-only (TR:337-339, RSM:55-68).
- **enqueueUpload**: FJP build workers or render thread via compileSync, NO copyLock held (TR:38-41), call site SBT:125.
- **onSectionCompiledEmpty**: build thread (TR:1126-1128), call sites SBT:72, SBT:83.
- **onTranslucentResort**: build worker OR render thread, under copyLock (RSM:119-131, RSM:160).
- **disposeAndReset/KeepingSeam**: render thread (MTP:23-27, MTP:154, MTP:166).
- **attachArena**: render thread, once per world, during pump-triggered standup (MTG:298 inside finishCreate ← MesheliumTerrainGpu.create() ← MTP:67 inside afterVanillaTerrainUpload).
- **drawSnapshot / drawer use**: render thread, TD:1646 in drawOpaqueInner, OUTSIDE the dispatcher.lock window (draw pass, not the upload window).
- **requestPinnedGrow**: client tick thread, MesheliumExtendedRd.java:672, pure volatile write (TR:405-413) — not snapshot state.

## 3. RegionStore side effects — the third-party [18] rewrite (the biggest log hazard)

`RegionStore.remove` is swap-remove (RS:221-274): when the removed slot isn't the tail, the TAIL section's record moves into the hole and `pos2id[movedPos]` is rewritten (RS:237-252, specifically RS:250-252). That changes the MOVED (untouched, third-party) resident's compactedSlot, hence its snapshot `[18] = (region.id<<8)|slot` (RS:399-406). The epoch bump at the removal site makes the FULL rebuild correct, but a per-slot change log that records only "REMOVE(removedSlot)" silently misses the moved entry's [18] change → stale globalSectionIndex → wrong stamp-buffer index for the translucent occlusion gate (TR:756-763). Fix available cheaply: the moved owner is identifiable inside remove as `region.ownerByPos[region.id2pos[last]]` read before the swap — have RS.remove return/callback the moved Resident so residency appends SLOT_INDEX(movedEntrySlot, newValue). This fires on EVERY remove path: S2, S5, S7-S10, and S1's variant (a) (its retained predecessor sits at the same posKey — RS.remove there hits the owner-check RS:228 only after ownsSlot bookkeeping; note S1(a) parks via TR:1625 and the region slot was already rebound by addOrReplace in place at RS:196-205, so no compaction there — compaction is a remove-path-only hazard). Region-level deltas ride the same records: region created RS:182-194 (byKey.put RS:188), region destroyed RS:266-270 (byKey.remove RS:267), count RS:199/262, occupancy AABB derived from pos2id (RS:362-378), retainedMask RS:209/261/422. Warning for the drawer-side region map: snapshotRegions/snapshotRetainedMasks iteration order is fastutil-hash-map order, only stable while unmutated (RS:344-347, RS:429-433) — the incremental region map must key by regionId, never by index.

## 4. Aggregate answers

**(1) Can any mutation escape the LOCK?** No snapshot-reflected mutation can. Every site in §2 is inside `synchronized(LOCK)` — the hooks take it themselves (TR:875, 922, 1042, 1130, 1210, 1268) and everything else nests under the pump's hold (TR:1285). RegionStore has no lock of its own and is only called under residency's LOCK (RS:36-41). TerrainArena's handle-mutators (grow/shrink/append, TA:273/306/342) have no callers outside residency-under-LOCK post-attach. Lock-free writes exist but are all non-snapshot volatiles/thread-locals: pendingGrowOption (TR:409-413), pinnedGrowFailed (TR:471), lastError/guardTrip (TR:373, 509), RESET_DEPTH (TR:340, 998-1008).

**(2) Mutation between drawSnapshot's null-return and the drawer using its cached snapshot, same frame?** YES — from worker threads only. The drawer runs on the render thread outside the copyLock window (TD:1646 is in the draw pass, the pump's window closed at MTP:73's return), so render-thread mutators (pump, reset-bracket releases, dispose) are serialized against it by thread identity, but worker-thread onMeshReleased (doTask paths + seam checkSectionMesh RSM:214), onSectionCompiledEmpty (SBT:72,83), and onTranslucentResort can take LOCK and mutate + bump mid-draw. Today this is safe because every such mutation is CPU-only: parked ranges can't be reallocated for FREE_FRAME_LAG=3 pumps (TR:801-803, 1486-1500), and GPU records/handles change only inside the pump (RS:283-333 render-only per RS:40-41; S11-S14 pump-only). Also note within-frame coherence: TD:1646 is the ONLY drawSnapshot call site in the drawer (grep), so opaque refreshes and translucent reuses the same `snapshot` field — one snapshot per frame. Design consequence: the ping-pong applier must drain the log at ONE defined per-frame point (pump is the natural one — same LOCK, same window releases can't enter); deltas appended by workers after that point are next frame's, exactly like today's cached-snapshot staleness, and inherit the same fence-lag safety.

**(3) Epoch-bump rate while turning — the storm driver.** The per-streamed-section site is S1 (TR:1641): one bump per uploaded section per pump, bounded by UPLOAD_BYTES_PER_PUMP = 16 MiB (TR:144) — order 10²/pump at typical section sizes. Turning exposes never-compiled sections → compile (workers) → enqueueUpload (no bump) → next pump's drain bumps once per section. A REBUILT section costs 2 bumps: old release lands with the successor already queued (new-mesh ctor precedes old release, TR:82-87) → handover-retain S3 (TR:1085), then S1 which also removes the retained predecessor under the same 1641 bump (TR:1610-1626). Grid-reposition streaming adds S4/S2 per section leaving range. Every bump collapses into one full O(n·20-int + regions + masks + TD rebuildRegionMap TD:1650) rebuild per frame at TD:1646-1651 — that's the 0.072→2.831 ms p50 and the ~280 MB/s garbage. Log sizing: worst frames are not turning but release storms — releaseAllBuffers routes every section through reset-bracketed releases in ONE frame (TR:75-78), thousands of records → that's the log-overflow → full-rebuild fallback case, plus dispose (S6) which must force it. Eviction sweeps are bounded contributors (≤256+64/pump, TR:327-329).

**(4) In-place Resident mutation without its own epoch bump — the dangerous class.** Field census (Resident TR:174-214): mutable fields are ownsSlot, orphanedAtMillis, translucent innards. Every write site: ownsSlot TR:1619, TR:1628 (both covered by the same iteration's bump at TR:1641 — no epoch-free path, verified: no continue/throw between except OOM-class); orphanedAtMillis TR:1080, TR:1098 (bump-adjacent, and not snapshot-read anyway); translucent.prefix/order/dirtySinceEncode TR:950/956/961/1638 (no bump, not snapshot-read — correct). So NO epoch-free in-place mutation of packed-entry inputs exists in TR itself. The two real dangers for the LOG (not the epoch): (a) the swap-remove third-party [18] rewrite, §3 — epoch-covered, log-invisible without the moved-owner record; (b) TR:1628's live-slot-steal [18]→−1 — same shape, must be an explicit record; plus (c) attachArena S15, the one genuinely bump-free snapshot-state write, benign only via the maps-empty invariant. `[18]` being computed-not-stored (TR:844-846) means the applier must recompute the packed [18] for: the written slot, the slot-steal victim, and the compaction-moved entry — that set, exactly.
